== Getting Quart Set Up Using a [keep-together]#Functional Test#

Test-driven development isn't something that comes naturally.
It's a discipline, like a martial art, and just like in a Kung Fu movie,
you need a bad-tempered and unreasonable master to force you to learn the discipline.
Ours is the Testing Goat.


=== Obey the Testing Goat! Do Nothing Until You Have a Test


((("Testing Goat", "defined")))
The Testing Goat is the unofficial mascotfootnote:[
OK more of a minor running joke from PyCon in the mid 2010s,
which I am single-handedly trying to make into a thing.]
of TDD in the Python testing community.
It probably means different things to different people,
but, to me, the Testing Goat is a voice inside my head
that keeps me on the True Path of Testing--like
one of those little angels or demons that pops up by your shoulder in the cartoons,
but with a very niche set of concerns.
I hope, with this book, to install the Testing Goat inside your head too.

So we've decided to build a web app, even if we're not quite sure what it's going to do yet.
Normally, the first step in web development is getting your web framework installed and configured.
__Download this, install that, configure the other, run the script__...but TDD requires a different mindset.
When you're doing TDD,
you always have the Testing Goat inside
your head--single-minded as goats are--bleating
``Test first, test first!''

In TDD the first step is always the same: _write a test_.

_First_ we write the test; _then_ we run it and check that it fails as expected.
_Only then_ do we go ahead and build some of our app.
Repeat that to yourself in a goat-like voice.  I know I do.

Another thing about goats is that they take one step at a time.
That's why they seldom fall off things, see, no matter how steep they are—as you can see in <<tree_goat>>.
[[tree_goat]]
.Goats are more agile than you think (source: Caitlin Stewart, on Flickr)
image::images/tdd3_0101.png["A picture of a goat up a tree", scale="50"]


We'll proceed with nice small steps;
we're going to use _Quart_, which is a popular Python web framework, to build our app.
Quart is the async cousin of Flask, so it will feel familiar if you've seen either of them.


((("Quart framework", "set up", id="QTsetup01")))
The first thing we want to do is check that we've got Quart installed
and that it's ready for us to work with.
The _way_ we'll check is by confirming that we can spin up a web server
and actually see it serving up a web page, in a web browser, on our local computer.
We'll use the _Playwright_ browser automation tool for this.((("Playwright")))

But before we can write even one test, we need somewhere to put it.
So, a quick bit of setup.
We'll do all of our Python project management with _uv_,
which you installed in &#x201c;<<pre-requisites>>&#x201d;.
Let's ask it to create a new project for us, called _superlists_,
and then step inside:

[subs="specialcharacters,quotes"]
----
$ *uv init --lib --python 3.14 superlists*
$ *cd superlists*
----

((("uv", "creating a project")))
That makes a folder with a few files inside it.
The ones to notice are _pyproject.toml_, which describes our project,
and _src/superlists/_, which is where our application code is going to live:

[role="skipme"]
----
superlists
├── .gitignore
├── .python-version
├── README.md
├── pyproject.toml
└── src
    └── superlists
        ├── __init__.py
        └── py.typed
----

NOTE: There's no virtual environment for you to create or activate.
    uv will make and manage one for us, in a _.venv_ folder, the first time we need it,
    and whenever we use `uv run` to run something, it runs inside that environment.

Now let's add the things we know we're going to need:
Quart itself, and Hypercorn, which is the server we'll use to run it.
Then, for testing, we want _pytest_, and its Playwright plugin,
which will let us drive a real browser from our tests:

[subs="specialcharacters,quotes"]
----
$ *uv add quart hypercorn*
$ *uv add --dev pytest pytest-playwright*
----

Finally, Playwright needs to download the browser it will control.
We'll use Chromium. It's a biggish download, so it may take a minute:

[subs="specialcharacters,quotes"]
----
$ *uv run playwright install chromium*
----

[[first-FT]]
((("functional tests (FTs)", "creating")))
Now we can write our first test.
Create a new file called _tests/functional/test_first_visit.py_,
(you'll need to make the folders too),
and enter the following code.
If you feel like making a few little goat noises as you do it, it may help:

[role="sourcecode"]
.tests/functional/test_first_visit.py
====
[source,python]
----
from playwright.sync_api import Page


def test_can_visit_the_site(page: Page):
    page.goto("http://localhost:8000")

    assert "To-Do" in page.title()
----
====

That's our first _functional test_ (FT);
I'll talk more about what I mean by functional tests,
and how they contrast with unit tests, in a bit.
For now, it's enough to assure ourselves that we understand what it's doing:

- It's a plain pytest test function, and pytest-playwright hands it a `page`,
  which is a tab in a real Chromium browser.((("Playwright", "page fixture")))((("Chromium")))

- It uses the page to open up a web page, which we're expecting to be served from the local computer.

- It checks (makes a test assertion) that the page has the word "To-Do" in its title.

- If the assertion fails, pytest tells us. If all goes well, the test passes.

Let's try running it:

[subs="specialcharacters,quotes"]
----
$ *uv run pytest tests/functional*
[...]
tests/functional/test_first_visit.py F                                   [100%]
[...]
E           playwright._impl._errors.Error: Page.goto:
net::ERR_CONNECTION_REFUSED at http://localhost:8000/
[...]
FAILED tests/functional/test_first_visit.py::test_can_visit_the_site[chromium]
[...] 1 failed in 1.66s [...]
----

[role="pagebreak-before"]
That's a lot of output for one little failure, but you only need to look for
the line that starts with an `E`, for "error".
It says `net::ERR_CONNECTION_REFUSED`,
which is Chromium's way of telling us that it went to _localhost:8000_,
knocked on the door, and nobody was home.
It ran headless, so you won't have seen a browser window pop up.
That's what we want for now;
if you're curious, adding `--headed` to the pytest command will show you the browser at work.

NOTE: If, instead, you see an error trying to import `playwright`,
    or one telling you that the browser executable doesn't exist,
    you might need to go back and have another look
    at the &#x201c;<<pre-requisites>>&#x201d;,
    or re-run the `playwright install` command.


For now though, we have a _failing test_,
so that means we're allowed to start building our app.




=== Getting Quart Up and Running

((("Quart framework", "set up", "app creation")))
Unlike some bigger frameworks, Quart doesn't have a big command-line tool
that generates a project full of files for us.
A Quart app can be as small as a single file with a single function in it.
That's all we need to get our test passing, so that's what we'll write.
Open up _src/superlists/\__init__.py_,
which uv created for us, and replace its contents entirely:

[role="sourcecode"]
.src/superlists/+++__init__+++.py
====
[source,python]
----
from quart import Quart

app = Quart(__name__)


@app.get("/")
async def home_page():
    return "<html><title>To-Do lists</title><h1>To-Do</h1></html>"
----
====

That creates an `app`, and tells it that when someone asks for the home page, _/_,
it should respond with a tiny bit of HTML containing our title.
If the `async def` is new to you, don't panic.
It just says that this function can be paused while it waits for things like
network or database access, so that the server can get on with other requests in the meantime.
We won't need to think about it much for a while.

((("development server", "running with Hypercorn")))
((("Hypercorn")))
To actually serve the app, we use Hypercorn.
The argument says "in the package called `superlists`, find the thing called `app`":

[subs="specialcharacters,quotes"]
----
$ *uv run hypercorn superlists:app*
[...] [INFO] Running on http://127.0.0.1:8000 (CTRL + C to quit)
----

That's our web server up and running on our machine.

Leave it there and open another command shell.  Navigate to your project
folder, and then try running our test again:

[subs="specialcharacters,quotes"]
----
$ *uv run pytest tests/functional*
[...]
tests/functional/test_first_visit.py .                                   [100%]
[...]
[...] 1 passed in 0.75s [...]
----

Not much action on the command line, but you should notice two things: firstly,
there was no ugly `E` error and, secondly, the `F` has turned into a `.`,
and pytest tells us `1 passed`.((("AssertionError")))

TIP: If you see `ERR_CONNECTION_REFUSED` again, check that the server is still running
    in the other shell, and that it says it's listening on port 8000.
    If something else on your computer is already using that port,
    Hypercorn will refuse to start, and tell you so.

Well, it may not look like much, but that was our first ever passing test!
Hooray!


If it all feels a bit too much like magic, like it wasn't quite real,
why not go and take a look at the server manually,
by opening a web browser yourself and visiting pass:[<em>http://localhost:8000</em>]?
You should see a very plain page, with the word "To-Do" on it, in big letters.

You can quit the server now if you like,
back in the original shell, using Ctrl+C.


.Adieu to Roman Numerals!
*******************************************************************************
So many introductions to TDD ((("Roman numerals in examples")))use Roman numerals in their examples
that it has become a running joke--I even started writing one myself.
If you're curious, you can find it
on https://github.com/hjwp/tdd-roman-numeral-calculator[my GitHub page].

Roman numerals, as an example, are both good and bad.
It's a nice "toy" problem, reasonably limited in scope,
and you can explain the core of TDD quite well with it.

The problem is that it can be hard to relate to the real world.
That's why I've decided to use the building of a real web app,
starting from nothing, as my example.
Although it's a simple web app,
my hope is that it will be easier for you to carry across to your next real project.

In addition, it means we can start out using functional tests
as well as unit tests, and demonstrate a TDD workflow that's
more like real life, and less like that of a toy project.

=== Starting a Git Repository

((("Git", "starting repositories")))
((("version control systems (VCSs)", seealso="Git")))
There's one last thing to do before we finish the chapter:
start to commit our work to a _version control system_ (VCS).
If you're an experienced programmer, you don't need to hear me preaching about version control. But if you're new to it, please believe me when I say that VCS is a must-have.
As soon as your project gets to be more than a few weeks old and a few lines of code,
having a tool available to look back over old versions of code,
revert changes, explore new ideas safely, even just as a backup...It's hard to overstate how useful that is.
TDD goes hand in hand with version control,
so I want to make sure I impart how it fits into the workflow.

.Our Working Directory Is Always the Folder That Contains pyproject.toml
******************************************************************************
We'll be using this same folder throughout the book
as our working directory--if in doubt, it's((("pyproject.toml file", "working directory containing"))) the one that contains _pyproject.toml_.

(For simplicity, in my command listings, I'll always show it as: _...goat-book/_. Although it will probably actually be something like:
_/home/kind-reader-username/my-python-projects/superlists/_.)

Whenever I show a command to type in, I will assume we're in this directory.
Similarly, if I mention a path to a file, it will be relative to this directory.
So, for example, _src/superlists/\__init__.py_ means the _\__init__.py_ inside the _src/superlists_ folder.

******************************************************************************


So, our first commit!
If anything, it's a bit late; shame on us.
We're using _Git_ as our VCS, ’cos it's the best.

Good news: we don't have to do the `git init`.
When uv created our project, it noticed we weren't inside a repository already,
and started one for us.
It also wrote us a _.gitignore_ file, which, um, tells Git what to ignore.((("Git", "commits")))((("default branch name in Git")))((("Git", "default branch name, choosing")))(((".gitignore file", primary-sortas="gitignore")))
Let's take a look at it:

[subs="specialcharacters,macros"]
----
$ pass:quotes[*cat .gitignore*]
# Python-generated files
__pycache__/
*.py[oc]
build/
dist/
wheels/
*.egg-info

# Virtual environments
.venv
----

Our virtual environment and all those `__pycache__` folders are on the list,
so they won't end up in version control.
That's one fewer thing to think about.
Let's add everything else and see where we are:

[subs="specialcharacters,macros"]
----
$ pass:quotes[*git add .*]
$ pass:quotes[*git status*]
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)

        new file:   .gitignore
        new file:   .python-version
        new file:   README.md
        new file:   pyproject.toml
        new file:   src/superlists/__init__.py
        new file:   src/superlists/py.typed
        new file:   tests/functional/test_first_visit.py
        new file:   uv.lock
----

.Setting the Default Branch Name in Git
*******************************************************************************

If your `git status` says `On branch master` rather than `main`,
that's just Git's old default branch name.
((("default branch name in Git")))
I chose `main`, it's a popular choice, and you might see it here and there in the book.
So if you want to match that, do:

[role="skipme"]
[subs="specialcharacters,quotes"]
----
$ *git branch -m main*
$ *git config --global init.defaultBranch main*
----

The second command makes all your future repositories start out that way.

*******************************************************************************

TIP: You'll see I'm using `git status` a lot--so much so that
    I often alias it to `git st`...I'm not telling you how to do that though;
    I leave you to discover the secrets of Git aliases on your own!((("aliases in Git")))


Looking good--we're ready to do our first commit!

[subs="specialcharacters,quotes"]
----
$ *git commit*
----
